# Outreach sample-call recordings + visual emails — implementation plan

Spec (binding): the founder's request — make vertical outreach emails more compelling by (1) recording a real sample call relevant to each vertical on our platform, hosting it, and linking it from the email; (2) measuring whether recipients actually open the recording/transcript (experimental); (3) putting a visually appealing transcript snippet in the email; (4) exploring how to make the emails visually appealing. Context from a teammate: the existing "mystery shopper" (realtime-tts/call-loop-poc) is an internal Retell-vs-us A/B harness (AI shopper persona places Twilio calls, Twilio records both channels, recordings are hosted by Twilio and swept by a retention job); it is not a sales-demo generator.

Repo: this worktree (github.com/tsushanth/calldesktech, branch `outreach-samples`, cut from main f3026ae). Outreach code lives in `src/lib/outreach/`, admin UI in `src/app/admin/outreach/`, sender in `src/lib/outreach/sender.ts` (builds the HTML/text email at send time from `msg.body_text` + footer; a human clicks Send in the queue, nothing is automated).

## Global constraints (bind every task)
- **Sample content:** a sample is an AI shopper calling OUR OWN Calldesk demo agent on OUR OWN numbers about a FICTIONAL business in the vertical. Never a real business, never a prospect's name/data. One sample per vertical (product id like `calldesk:freight`), not per lead. Every place a sample appears must disclose it is an AI-to-AI demo call.
- **Email:** plain text stays the primary content; a text alternative always exists and includes the link. HTML is light: table-based layout, inline CSS, no required remote images, one call-to-action, no tracking pixel (no open-tracking). If a vertical has no published sample, or anything about samples fails, the email is byte-for-byte what it is today.
- **Tracking (first-party only):** the link goes to our own page with a per-message signed token; record `view` (page load), `play`, `complete` events. Ignore bots/link-scanners. Store no IP address. Dedupe so repeated reloads don't inflate "unique viewers".

### Task 1: Data model and samples library

Create migration `supabase/migrations/043_outreach_samples.sql` (do not apply):
- `calldesk_outreach_samples`: id uuid pk default uuid_generate_v4(), product text not null (e.g. `calldesk:freight`), title text, business_name text (the fictional business), disclosure text not null, audio_path text (Supabase Storage object path in a PRIVATE bucket `outreach-samples`), audio_duration_sec int, transcript jsonb not null (array of `{speaker:'caller'|'agent', text}`), snippet jsonb (array of transcript indexes to show in emails, 4-6 lines), published boolean not null default false, created_at timestamptz default now(). Partial unique index so at most one published sample per product.
- `calldesk_outreach_sample_events`: id uuid pk, message_id uuid (nullable; FK not required), sample_id uuid, product text, event text check in ('view','play','complete'), is_bot boolean not null default false, created_at. Indexes on (message_id, event) and (sample_id, event).
- `ALTER TABLE calldesk_outreach_messages ADD COLUMN IF NOT EXISTS variant text, ADD COLUMN IF NOT EXISTS sample_id uuid;` (variant values `plain` | `sample`).
- `ENABLE ROW LEVEL SECURITY` on both new tables, no policies (service role bypasses; anon gets nothing). Follow the existing migration style (see 032, 042; note `uuid_generate_v4()` is used by existing tables).

Create `src/lib/outreach/samples.ts` exporting (typed, no `any` leaking out):
- `sampleTokenFor(messageId)` / `verifySampleToken(token) -> messageId | null`: HMAC-SHA256, same secret source as `src/lib/outreach/unsubscribe.ts` (`UNSUBSCRIBE_SECRET || CRON_SECRET`), but domain-separated (prefix the signed payload, e.g. `sample:`), so an unsubscribe token can never validate as a sample token and vice versa. Use `timingSafeEqual`. Token safe in a URL.
- `productSlug(product)` / `productFromSlug(slug)`: `calldesk:freight` <-> `freight`; reject anything that is not a known outreach product id shape.
- `getPublishedSample(supabase, product)`: returns the published sample row or `null`; returns `null` (logs once at warn level) on ANY error including missing table.
- `pickVariant(messageId): 'plain' | 'sample'`: deterministic 50/50 by hash of the message id (stable across calls), overridable by env `OUTREACH_SAMPLE_VARIANT` = `sample` | `plain` | `ab` (default `ab`).
- `sampleUrl(baseUrl, product, token)`: `<base>/samples/<slug>?t=<token>`.
- `snippetLines(sample)`: resolves `snippet` indexes into `{speaker,text}` lines, capped at 6, falling back to the first 5 transcript lines if `snippet` is missing/invalid; text truncated per line (~140 chars, on a word boundary, with an ellipsis).
- `isBotUserAgent(ua)`: true for empty UA and common crawlers/link-preview/email-security scanners (Googlebot, bingbot, Slackbot, facebookexternalhit, LinkedInBot, WhatsApp, Twitterbot, Microsoft Preview, Barracuda, Proofpoint, Mimecast, python-requests, curl, HeadlessChrome, etc.).

Tests in `test/lib/outreachSamples.test.ts`: token round-trip, tamper/wrong-secret rejection, unsubscribe token rejected as a sample token, slug mapping (accepts real product ids, rejects junk), variant determinism and env override, snippet resolution/fallback/truncation, bot detection cases, `getPublishedSample` returns null on a rejecting mock client.
