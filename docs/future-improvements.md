## Agent tests: graph-driven callers and field-level assertions

Today (`src/lib/testCaseSimulator.ts`, `/api/agents/[id]/test-cases`): a test case is a name, a caller goal
(`user_prompt`) and plain-English `success_criteria`. Cases are generated by Opus from the agent's published
flow, so they cover its branches. At run time the caller is a goal-only Haiku prompt talking to the flow over
text via `textFlowEngine`, for at most 8 turns, and an Opus judge gives pass/fail on the transcript.

Gaps:
- The caller does not follow a graph or script, so runs are non-deterministic and there are no stress
  behaviors (vague caller, misread digits, changes their mind, off-topic question, "what?").
- No field-level assertions (recorded name/time/number) and no "must never accept value X" check.
- Tests run on `textFlowEngine`, not call-loop-poc's voice engine, so they cannot exercise the voice path or
  compare LLMs per flow, and the two engines can diverge.

Idea: give a test case an optional caller level (prompt | script | graph), a shopper flow or script, and an
`expect` block (final field values, forbidden values). Keep the Opus judge for open-ended criteria. Let the
generator emit graph shoppers for the stress behaviors from the agent's own flow, run on the same engine as the
agent. Prototype of the three levels: a bake-off harness driving a shopper as a second call-loop session
(graph = flow with an "always" opening exit, script = full-script prompt, prompt = goal only).
Touches schema, runner, generator and UI; decide the engine question first.
